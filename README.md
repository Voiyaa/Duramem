# Duramem

**挂载式 LLM 记忆服务。** 给 AI 聊天窗口装一份独立于窗口的记忆——对话原文存在你自己的
SQLite 文件里，换个窗口、换个客户端，记忆都还在。

它不是一个更聪明的摘要器。它的做法是：把对话切成**记忆切片**，而每个切片同时承担两个角色——
它既是**被召回的记忆**，也是**指向原文的索引**。所以定位用摘要，核对细节时能回到逐字的原话，
两者是同一条记忆的两种粒度，不会互相矛盾。

- 一个库 = 一个 `.db` 文件，`sqlite3` 就能打开看，可导出、可拷贝、可交接
- 向量 + FTS5 词法**两路并行**检索，RRF 融合，重排可选
- 分层按需深入：摘要 → 会话概览 → 原文，由模型自己决定走多深
- 单用户、本地部署、无鉴权 —— 它假设跑在你自己机器上

---

## 为什么不能让 agent 自己压缩

主流做法是让 agent 在上下文快满时自己总结一段。问题不在"总结得不好"，而在三件事：

1. **有损且不可见。** 你无法审计它丢了什么，也无法只补回某一句原话。
2. **它属于那个窗口。** 关掉窗口，压缩结果一般也跟着没了。
3. **它对"细节型问题"结构性失效。** 摘要天然会丢掉错误码、文件路径、行号、精确措辞——
   而人回头看聊天记录，十次里有八次问的正是这些。

Duramem 把这件事挪出窗口：原文全文入库，检索走独立服务，并让模型在需要细节时
**能自己回查**，而不是隔着一次有损压缩硬答。

## 三个设计判断

### 一、切片既是记忆，也是原文索引

一段对话被切成若干切片，每个切片记住 `msg_id_start..msg_id_end` 区间与**字符偏移**。
区间由服务端从消息区间重新渲染得出，**不采信模型自述的字符数**——模型能准确判断
"哪几条消息属于这个记忆"，让它数字符必然错。测试里有一条不变式断言覆盖全部切片：
切片存的原文必须逐字等于 `messages[区间]` 的渲染结果。

消息被编辑时，受影响的切片原文会同步重渲染（否则"切片即索引"就名不副实），
但**不动切片摘要**——那是模型当时的判断，不该被静默改写。

### 二、三层，每层只干一件事

| 层 | 挂在哪 | 是什么 | 怎么拿 |
|---|---|---|---|
| **切片摘要** | 切片 | ≤256 token，进向量与 FTS5 索引，是进上下文的那一份 | `dm_search` 直接返回 |
| **会话简介** | 会话 | ≤256 token 的定位句，从概览首段**机械抽取** | `dm_search` 命中会话时返回 |
| **会话概览** | 会话 | ≤1600 token 的**地图**：叙事主线、覆盖度盲区、uid 导航 | `dm_read_session` |
| **切片原文** | 切片 | 逐字对话，带精确字符区间 | `dm_read_original` |

概览与简介**一次模型调用产出两层**（简介是概览正文里第一个二级标题之前那段），
所以两层永不互相矛盾，也没有额外成本。

概览刻意是地图而不是缩印本：它由各切片的摘要聚合生成，逐条重述的信息量本就是摘要的
子集（是派生冗余），所以它只保留摘要给不出的三样——跨切片的叙事主线、覆盖度盲区、
以及"想知道什么 → 读哪个 uid"的导航。

### 三、是否深入，由模型决定；服务负责给出判断依据

服务不猜模型够不够用，而是把判断所需的事实摆在返回体里：`has_original`（原文在不在）、
`msg_range`（区间在哪）、`session_id`（能不能去取会话概览），以及 `_suggestion` 里
针对这条命中的具体建议——摘要是否已达长度上限、存在相邻切片可以补全上下文等。
结果普遍偏弱时另外给一条显式告警，让模型能说出"没检索到"，而不是拿一堆弱相关摘要硬答。
没有这些信号，"自主回查"会变成一个模型永远不用的功能。

反过来，**不设读取限额**。曾经有过"每轮 4000 token 预算、超额拒绝"的设计，实测伤害很大：
一条 7956 token 的区间被拒后只能拿到 500 token 的摘要，丢掉 94%，而现代上下文完全装得下。
现在返回体如实报告这次花了多少 token，把节约交给"定位精度"（精确 uid + 消息区间）
而不是硬限额。

## 检索怎么跑

```
       ┌─ 向量路：嵌入 → sqlite-vec KNN（带相关性下限）
query ─┤
       └─ 词法路：jieba 分词 → FTS5 BM25
                │
                ▼
           RRF 融合（两路都按排名参与）
                │
                ├─ 可选重排（默认关闭）
                │
                └─ 可选图扩散（PPR：命中不足 / 结果偏弱 / 重排分平坦时触发）
```

几个刻意的选择：

**两路都跑，不是"词法兜底"。** 向量检索不会"失败"——它会自信地召回一堆语义相近的
错东西，重排分数还很高。而 `ERR_CONN_REFUSED_0x7f`、文件路径、项目代号这类查询，
向量表征很差、词法一次命中。两路并行、按排名融合（`Σ 1/(k+rank)`），
天然免疫两路分值的量纲差异。

**融合只用排名，不用分数过滤。** 实测单文档语料下 BM25 命中会返回 `-0.0`（IDF 趋零），
按分数设阈值会误杀正确命中。排名始终可靠。

**中文分词保留受保护 token。** jieba 会把 `ERR_CONN_REFUSED_0x7f` 切成
`ERR / _ / CONN / _ / REFUSED / _ / 0x7f`，而且它的块切分正则在词典介入之前就按 `/`、`:`
切开，`add_word` 对路径无效。所以实现里先用正则识别错误码、标识符、路径、版本号，
并**额外**作为独立词项入索引——整串与碎片两种粒度都保留，整路径查询和 basename 查询都能命中。

**图扩散是增补，不是替换。** 触发时从直接命中沿链接图做 PPR，把多跳相连、查询词够不着的
切片放进独立的 `expanded` 数组。直接命中一个字节都不动，所以"关掉开关 = 回到没有它之前"
是可验证的。

## 两种挂法

MCP 协议本身**读不到宿主的对话历史**，所以"挂载"实际是两个独立的集成面：

| | MCP（主动模式） | 记忆网关（被动模式） |
|---|---|---|
| 宿主要做什么 | 配一个 MCP server | 把 `base_url` 指向本服务 |
| 模型能做什么 | 自己决定何时查、查多深（7 个 `dm_` 工具） | 每轮自动收到相关摘要，没有工具权 |
| 原文采集 | 靠导入 / hook | **天然流经**，无需额外配置 |
| 适用 | 支持 MCP 的客户端 | 任何能改 `base_url` 的客户端 |

两条路可以同时开。网关的代价是模型只能被动接收，拿到的是摘要；MCP 的代价是需要宿主支持。

### MCP 工具

| 工具 | 作用 |
|---|---|
| `dm_search` | 检索切片摘要与会话简介 |
| `dm_read_original` | 回查原文：`quote`（精确区间）/ `window`（±N 条消息）/ `full` |
| `dm_read_session` | 读会话概览：`abstract`（仅简介）/ `overview` |
| `dm_read_neighbors` | 取相邻切片，补全跨切片上下文 |
| `dm_store` | 手动写入一条记忆（有限流——模型会滥用一切能写库的工具） |
| `dm_forget` | 软删除，界面可恢复 |
| `dm_stats` | 库状态，确认服务是否正常 |

**没有 `dm_summarize`。** 触发总结只由采集侧和界面调用；给模型这个能力它就会随意触发。

## 快速开始

### 先离线跑通（不需要任何 API Key）

不配 Key 时服务会自动进入离线模式：用确定性的哈希嵌入代替真模型。
向量检索、RRF 融合、回查、分层全部可用，只是没有语义泛化能力。这样可以先跑通整条链路，
再决定接哪个模型。

```bash
python -m venv .venv
.venv\Scripts\activate                             # Windows
# source .venv/bin/activate                        # macOS / Linux
pip install -e .

cp .env.example .env          # 可选；不填 Key 就是离线模式

duramem init --db work
duramem ingest messages.jsonl --db work --summarize   # 采集 + 切分
duramem search "上次那个错误码怎么解决的" --db work
duramem read <uid> --db work --mode window            # 回查原文
duramem refresh-sessions --db work                    # 生成会话概览
duramem stats --db work
```

### 起管理界面

后端直接托管前端构建产物（构建产物不入库，需要自己构建一次）：

```bash
cd frontend && npm install && npm run build
cd .. && duramem serve            # http://127.0.0.1:8001
```

不构建也能用——界面不存在时服务照常提供 REST 与 MCP。

| 页面 | 用途 |
|---|---|
| **库管理** | 多库、规模、模型一致性、总结游标；新建/重命名/快照/导出归档/导入归档；设为记忆库；按库编辑冷启动留言 |
| **切片浏览器** | 改标题（命名权）、改摘要、看原文与区间指针、软删除/恢复/真删 |
| **会话** | 按会话容器看记忆：简介列表 + 完整概览，导航里的 uid 可点，直接跳到那条切片 |
| **检索调试** | ★ 向量排名 / 词法排名 / RRF 融合排名**三路并列**，标出每条是仅向量、仅词法还是两路命中 |
| **记忆时间线** | 新增与命中分布、高频命中、会话与总结记录 |
| **导入对话** | 列出 → 勾选 → 预览 → 导入；也有一键导入未导入 |
| **模型** | 嵌入/重排/摘要的端点、模型名、维度、Key；预设 + 连通性测试 + 重建向量 |
| **设置** | 运行时参数，改完即时生效（对 MCP 侧进程同样热生效，不用重启会话） |

### 挂到聊天客户端

stdio 模式，`--data-dir` **务必写绝对路径**——stdio 子进程的工作目录由宿主决定，
不写就会把库文件生成在你当时打开的项目目录里：

```jsonc
{
  "mcpServers": {
    "duramem": {
      "command": "/path/to/Duramem/.venv/bin/duramem",   // Windows: ...\.venv\Scripts\duramem.exe
      "args": ["mcp", "--data-dir", "/path/to/Duramem/data"]
    }
  }
}
```

库由界面选定（库管理页「设为记忆库」）时，MCP 下一轮检索就跟着走，**不用重启会话**；
想钉死某个库就加 `--db <库名>`。远程或多窗口共用走 HTTP 模式：

```bash
duramem mcp --transport http --port 8001 --db work
```

#### 关于 hook 采集与宿主自身的压缩

有两条容易走偏的路，先说明白：

**hook 实时采集只适合"没有可读会话库"的宿主。** 宿主能导出结构化会话时，走「导入对话」
质量更高（角色完整、能按结构过滤、可排除子代理），而且不必每个事件同步等一次采集。
hook（`duramem hook-ingest`）保留给 SillyTavern、自定义客户端这类宿主；
它把日志全写 stderr、退出码恒为 0——采集失败不该阻塞你的会话。

**"不使用宿主自己的压缩"这条原则，各宿主可达程度差别很大。** 有的宿主能拦截自动压缩，
有的只能调压缩阈值，有的是完全没有相关钩子、只能靠 MCP 旁路。在拦不住的宿主上，
实际能做到的是**压缩后把记忆注回去**（效果接近，但不是同一件事）。
具体到某个宿主能不能拦，查它的 hook 文档，别假设。

### 把历史对话导进来

**挑着导，不要全量灌**——历史里大部分对话与当前要做的事无关，全灌只会让检索变差。

```bash
duramem sources                                  # 列出本机可导入的位置
duramem import --list                            # 列出可选对话（带序号）
duramem import --index 3 --summarize             # 导入第 3 个并切分
duramem import --session sess_xxx                # 按会话 id 精确导入
```

| 来源 | 位置 |
|---|---|
| `zcode` | ZCode 会话库（结构最规整，首选） |
| `rollout` | ZCode 模型往返日志 |
| `claude` | Claude Code 转录 |
| `dsh` | DeepSeek Harness 会话（zstd 多帧） |
| `generic` | 任意 JSON / JSONL，字段名容错 |

导入是**幂等**的（源会话 id 原样用作 `session_id`，`seq` 是它在原会话里的位置），
所以反复导入、分批导入、实时采集三者会正确合并，不产生重复记忆。源库全程 `mode=ro`
只读打开——ZCode 的库正被宿主使用，任何写入都可能损坏它。

实测一份真实历史，**83% 的内容不是对话**（宿主注入的 todo 提醒、后台通知、
助手在工具调用之间的叙述）。这些内容按**结构标记**（`semantics.origin`、
step 的结束原因）标为 `role=system`：不进摘要，但完整原文仍在库里可回查。

### Windows 一键脚本

```
start.bat        启动服务并自动打开界面
stop.bat         停止服务
check.bat        提交前三道门禁（ruff → mypy → pytest）
```

`stop.bat` **只按端口找进程，不按进程名杀**——Duramem 也会被宿主作为 MCP 子进程拉起
（同名 `duramem.exe`），按进程名杀会连带干掉正在用的会话。

## 实测

以下数字来自真实库（50 切片 / 1150 消息）在开发机上的实测，用来回答"该往哪里优化"。

**一次检索花在哪**（预热，真实模型）。中位 ~800 ms：

| 阶段 | 耗时 |
|---|---|
| 查询嵌入（BGE-M3，一趟 API 往返） | ~470 ms |
| 重排（bge-reranker-v2-m3，一趟 API 往返） | ~390 ms |
| **全部 Python + SQLite 计算**（分词、FTS5、KNN、RRF、图扩散、结果装配） | **~32 ms** |

这个 32 ms 是测出来的而非估的：把嵌入器与重排器都换成离线实现、并把 `httpx` 打桩成
"任何网络调用直接抛异常"之后，检索依然成功、零降级告警、零网络尝试。剩下的就是本服务
自己的全部计算量。

所以**延迟由模型往返决定**。想更快就换更近的端点，或关掉重排省掉一整趟往返
（`RERANK_ENABLED=false`），在本地抠 Python 收益很小。

**冷启动**：

| 路径 | 耗时 |
|---|---|
| 打开一个库（建组件 + 迁移） | ~10 ms |
| hook 采一次（含解释器启动） | ~320 ms |
| MCP 握手 | ~0.9 s，其中约 0.6 s 是 jieba 词典构建 |

向量后端是 `sqlite-vec` 的**暴力 KNN，没有 ANN 索引**。当前规模（几千到几万条切片）
下是毫秒级；到 20 万条量级需要换后端。向量访问已收敛在 `VectorIndex` 接口
（`add / remove / search / rebuild`）之后，换 [zvec](https://github.com/alibaba/zvec)
或 Milvus 只需另写一个实现类，不动调用方。

## 为什么做成"能打开看"的库

"数据可读、可改、可调试"是这个项目的第一取舍，具体落在几处：

**单文件 SQLite，主表不放二进制列。** 向量不在 `chunks` 表里，而在独立的 `chunks_vec`。
二进制列躺在主表里会让 `.dump`、DB Browser、导出 JSON 全是乱码；拆开后主表是纯文本，
向量可以 `DROP TABLE chunks_vec` 单独重建。

**身份与名字分离。** `chunk_uid` 是机器身份，创建后永不变，对外寻址只用它；
`title` 给人改，改了不影响 uid。库同理：显示名随便改、文件随便搬，身份由文件内的
`db_uuid` 保证；把库文件拷进数据目录会被自动收养。

**第三方一体化引擎被否掉过。** 例如 zvec 的单查询融合会把三路中间排名藏在内部——
而"能看到每一路各自把谁排在第几"恰恰是调参的唯一依据。自己实现融合，代价是多写几十行，
换来一整个可解释的调试面板。

**换嵌入模型时大声拒绝，而不是静默给噪声。** 旧向量与新向量不在同一个空间，
混着查只会得到无法解释的结果。所以改动向量身份（模型名/维度/端点/Key/强制离线）的
那一刻，相关库被标记为"需重建"，在重建完成前**拒绝检索**，界面直接列出是哪几张库。
重建中途失败也会留着标记，不会出现"元数据说正常、实际一条向量都没有"的库。

比对的不是模型名而是一个**来源指纹**（`db_meta.vector_source`）：配置里写的模型名和实际
跑的常常不是一回事——没填 Key 时服务会自动退到离线哈希，此时库里记着 `BAAI/bge-m3`，
而向量其实是哈希算的。只比名字会一路放行。

**归档是人类可读的 JSON，且能还原。** `duramem export` / `import-archive` 往返：
会话概览与总结游标都在（它们是花模型调用生成的），向量不在（可由当前提供方重建，
放进去只会把归档绑死在某一个嵌入模型上）。还原**只进新库不合并**，且消息 id 逐字保留——
切片的区间指针与总结游标都指向 `messages.id`，重新编号会让 window 模式静默失效。

## 一个库里有什么

一个库 = 一个 SQLite 文件（WAL 模式）。核心表：`messages`（原文）、`chunks`（切片，
纯文本 + 元数据）、`chunks_fts`（FTS5）、`chunks_vec`（vec0）、`session_layers`（会话层
概览与简介）、`links`（切片间被动链接，供图扩散）、`db_meta`、`summary_cursors`。

`vec0` 按固定块分配向量存储，块大小是建表选项 `VECTOR_CHUNK_SIZE`。sqlite-vec 默认 1024，
意味着**每个库带约 4 MB 固定下限**（1024 条 × 1024 维 × 4 字节），与库里实际有几条向量无关——
多库设计下这个开销会逐个累加。项目默认取 64。实测 16~1024 之间 KNN 延迟没有可测差异，
所以取小值只赚不亏。改它需要 `duramem rebuild-vectors`。

界面上的「库文件」大小刻意**不含 WAL 边车**，否则两个库看起来差不多大，
"一个文件 = 一份记忆"就没法用文件大小来支撑。

## 配置

全部键见 [`.env.example`](.env.example)（每一项都有中文注释说明为什么是这个默认值）。

模型相关（嵌入 / 重排 / 摘要的端点、模型名、维度、Key）建议在界面「模型」页改，
或 `duramem providers`——**改完立即生效不用重启**，写入 `data/provider_config.json`，
优先于 `.env`。密钥只写不读，保存后只回显掩码；留空保存表示保持不变，不会误删。
「测试连接」拿的是草稿，测的就是"保存后会怎样"，维度填错会在这里被拦下。

提供方统一走 OpenAI 兼容接口，内置硅基流动 / 阿里云百炼 / 本地 Ollama 的常用组合预设。

几个值得注意的：

```env
EMBEDDING_FAKE=false        # true = 离线哈希嵌入（无 Key 时自动开启）
RERANK_ENABLED=false        # 重排默认关闭：多一趟串行 API 往返
VECTOR_MAX_DISTANCE=0.9     # 余弦距离下限，刻意宽松，只剔除近似正交的结果
VECTOR_CHUNK_SIZE=64        # 建表选项，决定每库固定开销（见上）
OVERVIEW_ACCESS_ENABLED=true   # 关掉 = 模型只看得到摘要（日常模式）
ORIGINAL_ACCESS_ENABLED=true   # 关掉 = 模型看不到原文
TOKENIZER_EXTRA_WORDS=      # 项目代号、错误码等，保证不被切碎
```

## 边界

**明确不做**：多用户/多租户鉴权、云端同步与协作、知识图谱与实体关系抽取、
记忆的自动遗忘淘汰（只提供软删除与版本链，淘汰由用户决定）、ANN 近似索引。

**已知边界**：

- 向量检索是暴力 KNN，20 万条以上要换后端（见上）
- **摘要上限按 token 而不是字符**。同一个"256"，纯中文下约 150-200 token，
  而中英混排（带路径、代码标识符）下可能只剩 60-80——差三倍，所以不能用字符数来定限额
- 迭代检索环路只落地了前半段：图扩散（PPR）已上线，**编排层的子问题覆盖度信号未做**。
  多跳问题目前主要靠模型自己多问几轮
- **真实模型下的验收尚未做完**：自主回捞率、LoCoMo/LongMemEval 基线都还没有数字。
  离线测试覆盖的是机制正确性，不是检索质量

## 开发

```bash
check.bat                                          # 三道门禁：ruff → mypy → pytest
check.bat lint                                     # 只跑静态检查（几秒）
.venv/Scripts/python -m pytest -q                  # 全部测试
```

回归测试**全部离线**，不需要任何 API Key：`HashingEmbedding` / `OverlapReranker` /
`HeuristicSummarizer` 是确定性实现，它们的相似度是真实的（共享词项越多余弦越高），
所以"错误码查询应把含错误码的切片排在第一"这类断言是有意义的，不是为了让测试通过而写。
`tests/test_mcp_stdio.py` 会把服务作为**真实子进程**拉起来跑完整协议往返。
涉及"连不上模型接口"的用例一律打本机一个必然没人监听的端口，请求立刻失败、不发真实流量。

```
duramem/
  service.py          # 服务层门面，REST 与 MCP 共用（能力对等，改行为先改这里）
  mcp_server.py       # 7 个 dm_ 工具
  api.py              # REST 路由
  importing.py        # 历史导入 / 库快照 / 归档往返
  net.py              # 共享 HTTP 传输：单例 client + 缓存 SSL 上下文
  store/              # schema / registry / repository / session_layers / links
  retrieval/          # pipeline / fusion / lexical / vector_index / sessions / expand
  providers/          # embedding / rerank / presets / connectivity
  importers/          # ZCode / Claude Code / dsh / 通用 JSONL
  text/tokenize.py    # 分词与受保护 token
frontend/src/pages/   # 8 个管理页
tests/                # 离线测试
eval/                 # 迭代检索环路的评测集与结果
```
